# 一般公開の準備（守りのしくみと、公開の手順）

このアプリを、知らない人も使える形で公開するための準備です。
「身内では、できるだけ簡単に共有できる」ことと、「ほかのお店の販売会に入り込めない」ことの両方を目指しました。
しくみは、できるだけ単純にしています（**お店・端末を入れる・オーナー・お店の鍵**の4つだけ）。

> **大事なこと**：この文書は、アプリを作る側で確かめられる範囲のまとめです。
> 「どんな場合でも問題が起きない」と言い切ることはできません。下の「公開の手順」と「Firebase の設定」は、必ず運営する人が行ってください。

---

## 1. しくみ（これだけ）

```
          ┌──────── 置き場（インターネット・Firebase）────────┐
          │  お店ごとに分かれていて、お店の端末だけが読み書きできる   │
          └───▲──────▲──────▲──────▲────────────────┘
              │      │      │      │（CDは読むだけ）
          ［レジ］  ［レジ］  ［KD］  ［CD］   ← お店の端末（1台ごとに1回だけ入れる）
          オーナー

   お客様のスマホ（モバイルオーダー）… メニューと、自分の注文だけ
```

| ことば | 意味 |
|---|---|
| **お店** | 端末のまとまり。はじめて開店した端末がお店を作り、その端末がオーナーになる |
| **お店の端末（メンバー）** | お店に入れた端末。お店の販売会の売上・注文を見たり、会計したりできる。役割は オーナー／レジ（レジ・KD・ハンディ）／CD（映すだけ） |
| **端末を入れる** | オーナーの端末で押すと、QRコードと8文字の合言葉が**10分だけ**出る。新しい端末で読み取り、オーナーが**確かめる番号**を見比べて「入れる」を押す（1台ごとに1回だけ） |
| **合流** | お店のどれか1台が開店すると、ほかのお店の端末に「合流する」が出る。**押すだけ**（コードを打つことはない） |
| **オーナー** | 端末を入れる・外す・お店の鍵を作る。**2台以上**にしておくと、電池が切れても困らない |
| **お店の鍵** | 紙に印刷してしまっておく長い合言葉。オーナーの端末を全部なくした時に、新しい端末がオーナーになれる |

前の版（#65・#66）の「販売会ごとの許可・6けたのコード・1回だけの合言葉・いつもの端末」は、すべて上の形にまとめました（覚えることを減らすため）。

## 2. 守り（何から、どう守っているか）

| 心配 | 守り |
|---|---|
| 知らない人が、ほかのお店の販売会を見る・会計する | 置き場の決まり（`firestore.rules`）で、**お店の端末でなければ読み書きを断る**。アプリを改造されても、置き場が断る |
| 知らない端末が、お店に入りこむ | お店に入れるのは、**オーナーが「端末を入れる」を開いている10分の間**だけ。しかも ①合言葉（8文字・32種類の文字＝約1兆通り）②オーナーの「入れる」③確かめる番号の見比べ がそろった時だけ |
| 合言葉の写真を撮られる | 10分で使えなくなる。それでもオーナーが「入れる」を押さない限り入れない。「閉じる」ですぐ使えなくできる |
| 同じ名前の端末からのお願い | お願いを出した端末とオーナーの端末に、**同じ3けたの番号**が出る。番号が違えば断る |
| 端末の時計がずれている | 合言葉・鍵の期限は**置き場の時刻**で決める |
| 端末をなくした・盗まれた | オーナーの端末で「外す」と、**すぐに読めなくなる**。オーナーの端末なら「なくした端末を締め出す」（ほかのオーナーを全部外し、鍵を作り直す） |
| 開店した端末の電池が切れた | ほかのオーナーの端末で、端末を入れる・外すができる。オーナーが1台だけの時は、画面で控えをすすめる |
| オーナーの端末を全部なくした・記録が消えた | **お店の鍵**（紙）で、新しい端末がオーナーになれる。印刷したモバイルオーダーのQRコードもそのまま使える |
| だれかが勝手にオーナーになった | **お店の記録**（あとから直せない・消せない）に、だれがいつ端末を入れた・外した・鍵を使ったかが残る。鍵が使われた・オーナーが増えた時は、ほかのオーナーの端末に**知らせが出る** |
| お店の端末一覧に、使っていない端末が残る | 一覧に**「最後に使った日」**が出る。使っていない端末は「外す」 |
| お客様が、ほかの人の注文・お店の売上を見る | お客様が読めるのは、メニュー・公開用の設定・待っている組（時刻だけ）・**自分の注文だけ** |
| お客様が、値段・クーポンを書きかえる | レジが**レジの値段で数え直し**、クーポンは**コードを確かめ直して**から引く |
| いたずらの大量注文 | **1台のスマホから、1回の販売会で30件まで**（置き場の決まりで数える）。受付を止めることもできる |
| 注文・名前に、画面で動く書き方を入れる | レジ・KD・CD・印刷では**ただの文字**として出す（試験で確かめている） |
| ほかのページの中（見えない枠）にアプリを入れて、押させる | 枠の中では**表示しない**。`object`・`base` の差しこみも断る |
| 機械で大量に匿名ログインして、使用量を使い切る | **App Check**（設定するだけで有効。下の6）を入れると、このアプリ以外からの通信を断れる |
| 通信の返事が来ない | 15秒（App Check の時は30秒）で見切りをつけて、**この端末だけで営業**（会計は止まらない） |
| ブラウザが端末の記録を消す | アプリが「消さないで」とブラウザに頼む。iPhone は**ホーム画面に追加**して使う |

## 3. 端末に頼りすぎない（電池切れ・なくした・記録が消えた）

| こんな時 | 困ること | 控え・対処 |
|---|---|---|
| **開店した端末の電池が切れた** | 会計はほかの端末で続けられる。新しい端末を入れられない | 前もって、信頼できる人のレジを1台**「オーナーにする」** |
| **端末をなくした・盗まれた** | その端末がお店の売上を見られる | オーナーの端末で**「外す」**。オーナーの端末なら**「なくした端末を締め出す」** |
| **オーナーの端末を全部なくした** | だれも端末を入れられない | **お店の鍵**を使う。鍵が無い時は、新しい端末で開店（新しいお店になる）し、モバイルオーダーのQRを印刷し直す |
| **端末の記録が消えた**（ブラウザのデータを消した・別のブラウザ・iPhone の Safari で長く使わなかった） | ログインの印が変わり、お店に入っていない端末になる | もう一度「端末を入れる」から入れる。オーナーだった端末はお店の鍵を使う |
| 同じ iPhone で Safari とホーム画面のアプリを両方使う | 別々の端末として扱われる | どちらか一方だけを使う。QRコードはカメラで読むと Safari で開くので、ホーム画面のアプリには**合言葉を入力** |

### アカウント（メール・パスワード）にしなかった理由
- 名前・メールアドレスを集めないので、個人情報を守る負担と、漏れた時の害がありません。
- 利用者さん・職員さんがパスワードを覚えたり、ログインし直したりする必要がなく、会計の速さを落としません。
- 「メインのアカウント」にあたる物は、**オーナーの端末（2台以上）**と、**紙のお店の鍵**です。

## 4. 守りの確かめ（試験）

`tests/rules/` に、置き場の決まりの試験があります（Firestore エミュレーターで、本物と同じ決まりを当てて試す）。

```sh
cd tests/rules
npm i
npm test
```

確かめている主なこと（106項目）：お店を作る・端末を入れる（合言葉の期限・まちがい・端末の時計・ほかの人の名前・オーナーとしては出せない）・お店の端末だけが販売会を読み書きできる・CDは会計を読めない・お客様は自分の注文だけ・注文の上限30件・レストランの伝票の横取りができない・お店の鍵・お店の記録は消せない・前の版のお店の引きつぎ・外された端末はすぐ読めない・閉店後の片づけ。

アプリ本体も、エミュレーターにつないで通しで確かめています（開発用の試験。リポジトリの外）：
- お店のしくみの通し（48項目）：お店を作る・端末を入れる・断る・まちがい・閉じた後・CD・お客様の注文と上限・閉店と次の開店で「合流する」・自動で合流・開いている時の開店・控えのオーナー・電池切れ・外す・お店の鍵・締め出し・お店の記録と知らせ・前の版の引きつぎ・返事が来ない時の開店
- 上と同じ試験を App Check を有効にして（正しいキー・断られるキーの両方）
- 注文・お願い・端末の名前に、画面で動く書き方を入れても動かない（ファストフード・レストランで各14項目）

## 5. 公開の手順（この順番で）

1. **開いている販売会を、全部閉店する**（前の版で開いた販売会は、新しい決まりでは読めなくなるため）。
2. **アプリを、この版に更新する**（GitHub Pages に反映されるのを待つ。全部の端末で開き直す。ホーム画面のアプリは、一度閉じて開き直す）。
3. **置き場の決まりを公開する**（どちらか）。アプリの更新と、決まりの公開の間は、なるべく短くしてください（その間は共有がうまく動かないことがあります。会計は端末の中で続けられます）。
   - Firebase コンソール →「Firestore Database」→「ルール」に、リポジトリの `firestore.rules` の中身をそのまま貼って「公開」
   - または、パソコンで：`npm i -g firebase-tools` → `firebase login` → リポジトリのフォルダで `firebase deploy --only firestore:rules --project zemipos`
4. **お店を用意する**：オーナーにする端末で開店する（前の版でお店のオーナーだった端末は、そのままオーナーになり、印刷したQRコードもそのまま使えます）。
5. **端末を入れる**：オーナーの端末の「設定 → 複数端末で使う → 端末を入れる」で、ほかの端末を1台ずつ入れる。
6. **控えを作る**：信頼できる人のレジを1台「オーナーにする」。「お店の鍵」を作って印刷し、しまっておく。
7. **確かめる**：オーナーで開店 → ほかの端末に「合流する」が出る → 押す → 会計が両方に出る。
8. モバイルオーダーのQRコードは、前の版（`?s=…` が付いた物）ならそのまま使えます。`order.html` だけの古い物は印刷し直してください。

## 6. Firebase・Google Cloud の設定（運営する人が行う）

| 項目 | すること | なぜ |
|---|---|---|
| ログインの方法 | Authentication → Sign-in method で「匿名」だけをオン（ほかはオフ） | 使わない入口を閉じる |
| 匿名アカウントの自動削除 | Identity Platform にした場合、「匿名ユーザーの自動クリーンアップ」は**オンにしない** | オンにすると、しばらく使わない端末がお店から外れる |
| 承認済みドメイン | Authentication → Settings → 承認済みドメインを、アプリのドメイン（例：`inocozuchi.github.io`）と `localhost` だけにする | ほかのサイトから、このプロジェクトでログインさせない |
| APIキーの制限 | Google Cloud コンソール → 認証情報 → APIキー →「アプリケーションの制限：ウェブサイト」にアプリのドメインを入れ、「APIの制限」で Firestore・Identity Toolkit・Token Service・Firebase App Check だけにする | キーは公開されているので、使える場所と使い道をしぼる |
| **App Check**（強くおすすめ） | ①Google の reCAPTCHA（v3）の管理画面でサイトを登録し、アプリのドメインを入れて「サイトキー」を作る ②Firebase コンソール → App Check → ウェブアプリに reCAPTCHA v3 を登録（シークレットキーを貼る）③`data/firebase-config.js` の `APP_CHECK_SITE_KEY` にサイトキーを入れて公開 ④App Check の「指標」で、通信がほぼ全部「確認済み」になるのを数日見る ⑤Firestore を「適用（Enforce）」にする | 機械で大量に匿名ログインして、注文やお願いを大量に送ることを止める。④を飛ばして⑤をすると、まちがいがあった時に全部の端末が共有できなくなるので、必ず順番どおりに |
| 料金 | 無料プラン（Spark）のまま使うと、上限を超えた日はその日だけ止まる（請求は来ない）。従量課金（Blaze）にする時は、必ず「予算アラート」を設定する | だれかが大量に使った時に、思わぬ請求が来ないように |
| 使用量の見張り | Firestore の「使用状況」を時々見る | おかしな増え方に早く気づく |
| ほかの施設（`sites/`） | 同じプロジェクトを使う時も、置き場の名前は `events` のまま。**「ログインしていればだれでも読み書きできる」決まりを足さない** | 決まりは `events`・`shops` だけを守っている |

## 7. まだ残る心配と、その時の対処

| 心配 | 対処 |
|---|---|
| お店に入れた端末が、悪いことをする（会計を書きかえる等） | お店に入れるのは信頼できる人の端末だけにする。知らない端末は「外す」。会計の記録の変更は操作の記録に残る |
| オーナーにした端末が、悪いことをする（ほかの端末を外す等） | オーナーは本当に信頼できる人の端末だけにする。乗っ取られた時は、お店の鍵で取り戻し、「締め出す」。お店の記録で、何が起きたか確かめる |
| お店の鍵の紙を、人に見られた・なくした | すぐに「お店の鍵を作り直す」。見た人がもうオーナーになっていたら「締め出す」 |
| 端末の画面のロックが無く、置き忘れた端末を触られる | 端末のロック（パスコード）を使う。KD はレジと同じ権限なので、お客様の手の届く所に置かない |
| テーブルのQRコードを、ほかの席の人が使う | テーブルのQRの仕組み上、防げない（多くの店と同じ）。伝票の注文は、レジで取り消せる |
| レストランの伝票（テーブルごとの合計・支払い）が、お店の印を知っている人に読める | お客様の注文ページが、同じテーブルの伝票に注文を足すために読む必要がある。名前などは入っていない |
| クーポンのコードを当てずっぽうで探される | コードは長め（8文字以上）・数を限る（「上限」）にする。コードそのものは置き場に置かず、印だけを置いている |
| App Check を入れていない間の、大量の匿名ログイン・書き込み | 上の App Check を入れる。無料プランなら、その日だけ止まる |
| 全部の端末の電池が切れたまま閉店しなかった販売会 | 置き場に残るが、お店の端末しか読めない。気になる時は、Firebase コンソールで `events` の古い物を消す |
| 置き場の決まりを書きかえる時のまちがい | 書きかえたら、必ず `tests/rules` の試験を通してから公開する |

## 8. お店に知らせること（公開する時に用意するもの）

- **利用規約** と **プライバシーポリシー**：`docs/利用規約_案.md`・`docs/プライバシーポリシー_案.md` に案を置きました。公開する前に、運営する団体で中身を決め、できれば専門家に見てもらってください。決まったら、ホームページなどに置き、アプリの中からも見られるようにすると安心です。
- **問い合わせの窓口**（メールアドレスなど）：不具合・データを消してほしい時の連絡先。
- 端末のロック（パスコード）を使うこと、iPhone はホーム画面に追加して使うこと、オーナーを2台にしてお店の鍵を用意しておくことを知らせる。
