# 一般公開の準備（守りのしくみと、公開の手順）

このアプリを、知らない人も使える形で公開するための準備です。
「身内では、できるだけ簡単に共有できる」ことと、「ほかのお店の販売会に入り込めない」ことの両方を目指しました。
あわせて、「開店した端末の電池が切れた」「端末をなくした」など、**1台の端末に頼りすぎる危なさ**も調べて、控えを用意しました。

> **大事なこと**：この文書は、アプリを作る側で確かめられる範囲のまとめです。
> 「どんな場合でも問題が起きない」と言い切ることはできません。下の「公開の手順」と「Firebase の設定」は、必ず運営する人が行ってください。

---

## 1. いままでの穴（このままでは公開できなかった所）

| 穴 | 何が起きるか |
|---|---|
| 置き場の決まりが「ログインしていれば、だれでも読み書きできる」 | ログインは匿名なので、だれでもすべての販売会を読み書きできた |
| 共有コードが4けた（9,000通り） | 当てずっぽうでほかのお店の販売会に入れた。公開すると、コードも足りなくなる |
| 「いま開いている販売会」の一覧 | 世界中の開いている販売会が、だれの端末にも出ていた |
| 注文ページが、販売会の文書をまるごと読む | クーポンの印・担当者の名前・支払い方法の設定なども、お客様から見えていた |
| 注文ページが、ほかのお客様の注文も読む | ほかの人の注文の中身・メモが読めた |
| 印刷したQRコード（`order.html`）が、受付中のお店を全部探す | ほかのお店も一覧に出た |
| レストランの伝票の金額 | お客様のスマホが送った値段のまま数えていた（書きかえた値段で会計されるおそれ） |
| モバイルの注文のクーポン | 注文に書いてあるクーポンを、そのまま引いていた |
| 閉店した販売会の片づけ | 置き場の閉店した販売会を全部探していた（ほかのお店の分まで） |
| キッチンの見本（`sites/`）の説明 | 「ログインしていればだれでも読み書きできる」決まりを足すよう書いてあった（いまは消した） |

## 2. 新しいしくみ

### メンバーだけが入れる
- 販売会（`events/{コード}`）を読み書きできるのは、その販売会の**メンバー**の端末だけです。置き場の決まり（`firestore.rules`）で断ります（アプリを改造されても、置き場が断ります）。
- メンバーには3つの役割があります。
  - **オーナー**：合流の許可・端末を外す・合言葉を出す。開店した端末と、「お店のオーナー」にした端末
  - **レジ**（レジ・KD・ハンディ）：会計・注文・在庫
  - **CD**（CD・呼び出し番号）：映すだけ。会計の記録は読めず、書けません
- ログインは匿名のままです（名前・メールアドレスは聞きません）。端末ごとのログインの印で見分けます。

### メンバーになる道は4つだけ
1. **合流のお願い**（ふだん）：共有コード（**6けた**）を入れると、オーナーの端末に「◯◯が合流したいと言っています［許可］［断る］」が出ます。許可されると合流します。コードを知っているだけでは、中身は何も読めません。
   - お願いを出した端末と、オーナーの端末に、**同じ3けたの「確かめる番号」**が出ます。同じ名前の端末からお願いが来ても、番号を見比べれば、目の前の端末かどうか分かります。
2. **合流の合言葉・QRコード**（すぐ入りたい時）：オーナーの端末の「設定 → 複数端末で使う」で出します。**30分・1回だけ**使えて、許可を待たずに入れます（CD用・レジ用など、決めた役割でだけ）。
   - 1台が使うと、その合言葉は使えなくなり、オーナーの画面に次の端末用の新しいQRコードが出ます（画面を写真に撮られても、先に使われていれば入れません）。
   - 期限は置き場の時刻で決まります（端末の時計がずれていても、期限はずれません）。
3. **いつもの端末**（毎回の許可を省く。**初めはオフ**）：オーナーの端末で「次の開店でも、同じ端末を呼ぶ」をオンにすると、その販売会に入った端末を覚えます。次にその端末で開店すると、覚えた端末に「合流しますか」の知らせが届き、許可なしで入れます。KD・CD など置きっぱなしの端末は「お店から知らせが来たら、自動で合流する」をオンにすると、押さなくても合流します（これも初めはオフ）。
   - 知らせは、**入ったことのあるお店のオーナーから**の物だけを受け取ります。自動で合流するのは、知らせを出した端末が**いまもそのお店のオーナーの時だけ**です（締め出した端末からの知らせでは、合流しません）。
4. **お店のオーナー**：「オーナーにする」を押された端末と、「お店の鍵」を使った端末は、そのお店の販売会では、お願いを出さずに自動でオーナーになります（次の「端末に頼りすぎない」を見てください）。

### 外す・断る
- オーナーの端末の「設定 → 複数端末で使う」に、メンバーの一覧が出ます。知らない端末は「外す」で、すぐに読めなくなります（外された端末には知らせが出て、その端末だけの営業になります。その端末の中の記録は残ります）。**開店した端末も外せます**（なくした・盗まれた時のため）。
- 知らない人からのお願いが続く時は「合流のお願いを受け付けない」をオンにします（合言葉では入れます）。

### お客様（モバイルオーダー）
- 印刷するQRコードには、**お店の印**（`order.html?s=…`。変わらない印）だけを入れます。注文ページは、お店の印から「いま開いている販売会」を探します。ほかのお店は出てきません。
- お客様が読めるのは、メニュー・写真・お店の公開用の設定（`live/pub`）・待っている組（`live/queue`：作り始める時刻だけ）と、**自分の注文だけ**です。
- お客様が作れるのは「モバイル・未払い・調理中」の自分の注文だけ。払ったことにする・ほかの人の名前で作る・あとから書きかえることはできません。
- レジは、お客様の注文の**値段をレジの商品の値段で数え直します**（未会計の一覧・お会計・レストランの伝票）。クーポンは、お客様が入れた**コードをレジでもう一度確かめて**から引きます。
- 注文の名前・メモなどに、画面で動いてしまう書き方（`<img onerror=…>` など）を入れられても、レジ・KD・CD・印刷する伝票では、ただの文字として出します（試験で確かめています）。

## 3. 端末に頼りすぎない（電池切れ・なくした・記録が消えた）

このアプリは、名前やメールのアカウントを使わず、**端末ごとのログインの印**で見分けます。そのため「その端末が使えなくなった時」に困らないよう、次の控えを用意しました。

| こんな時 | 何が困るか | 控え・対処 |
|---|---|---|
| **開店した端末の電池が切れた・こわれた**（営業中） | 会計は、ほかの端末で続けられる。新しい端末の合流の許可・合言葉が出せない | 前もって、信頼できる人のレジを1台**「オーナーにする」**。その端末も合流を許可できる。オーナーが1台だけの時は、メンバーの一覧にすすめる文が出る |
| 同上（次の販売会） | 開店した端末でないと、印刷したモバイルオーダーのQRコードの行き先を変えられない | 「オーナーにする」を押された端末は**お店のオーナー**になり、お店の印も受けつぐ。その端末で開店しても、印刷したQRコードがそのまま使える。次からの販売会でも自動でオーナーになる |
| **端末をなくした・盗まれた** | その端末が、販売会を見たり、オーナーとして動いたりできてしまう | ほかのオーナーの端末で、その端末を**「外す」**（開店した端末も外せる。お店のオーナーからも外れる）。さらに**「なくした端末を締め出す」**で、ほかのオーナーを全部外し、お店の鍵を作り直し、いつもの端末も忘れる |
| オーナーの端末を**全部**なくした | だれも、お店のオーナーになれない | **「お店の鍵」**（下）を使う。鍵が無い時は、新しい端末で開店し、モバイルオーダーのQRコードを印刷し直す |
| **端末の記録が消えた**（ブラウザのデータを消した・別のブラウザで開いた・iPhone の Safari で長く使わなかった） | ログインの印が変わり、別の端末と同じ扱いになる。オーナーなら、お店のオーナーでもなくなる | 合流は、もう一度お願いを出す。オーナーだった端末は「お店の鍵」を使う。**iPhone はホーム画面に追加して使う**（Safari のままだと、しばらく使わないと記録が消されることがある）。アプリは、記録を消さないようブラウザに頼む（`navigator.storage.persist`） |
| 同じ iPhone で、Safari とホーム画面のアプリを両方使う | 別々の端末として扱われる（記録も別） | どちらか一方だけを使う。QRコードはカメラで読むと Safari で開くので、ホーム画面のアプリには**合言葉を入力**する |
| 電波が悪く、開店の書き込みの返事が来ない | 開店の画面で待たされる | **15秒で見切りをつけて、その端末だけで開店**する（会計はすぐできる）。あとで書き込みが届いた時のために、閉店の印と片づけを予約する |
| 端末の時計がずれている | 合言葉の期限がずれる | 合言葉の時刻は置き場の時刻で決める（端末の時計は使わない） |

### お店の鍵（初めは無し）
- オーナーの端末の「設定 → 複数端末で使う → 端末をなくした時のために → お店の鍵を作って印刷する」で作ります。紙に、QRコードと鍵（4文字ずつ5組・見まちがえやすい文字は使わない）が出ます。
- 新しい端末で「開店・合流 → お店の鍵を使う」に鍵を入れる（またはQRコードを読む）と、その端末が**お店のオーナー**になります。印刷したモバイルオーダーのQRコードもそのまま使え、開いている販売会があれば、オーナーとして合流できます。
- **この紙を持っている人は、だれでもお店のオーナーになれます。** 金庫・事務所など、お客様の目に触れない所にしまってください。なくした・見られた時は「お店の鍵を作り直す」で、前の鍵を使えなくできます。
- 鍵そのものは、置き場の中でも文書の名前にだけ置き、オーナーの端末しか読めません（鍵からお店を引く印は、鍵を知っている人だけが引けます）。鍵を使う時は「この鍵を持っています」を置き場の時刻つきで書き、10分のあいだだけ、自分をお店のオーナーに足せます。

### アカウント（メール・パスワード）にしなかった理由
- 名前・メールアドレスを集めないので、個人情報を守る負担と、漏れた時の害がありません。
- 利用者さん・職員さんがパスワードを覚えたり、ログインし直したりする必要がなく、会計の速さを落としません。
- 「メインのアカウント」にあたる物は、**お店のオーナーの端末（2台以上がおすすめ）**と、**紙のお店の鍵**です。パスワードを忘れる代わりに、紙をしまっておけば取り戻せます。

## 4. 守りの確かめ（試験）

`tests/rules/` に、置き場の決まりの試験があります（Firestore エミュレーターで、本物と同じ決まりを当てて試す）。

```sh
cd tests/rules
npm i
npm test
```

確かめている主なこと（105項目）：
- ログインしていない・知らない端末は、販売会・会計・予約・メンバー・CDの表示を読めない、書けない、探せない
- 共有コードを知っているだけでは、合流のお願いしか出せない（オーナーとしては出せない・ほかの人の名前では出せない）
- レジは、ほかの端末を足せない・自分をオーナーにできない・販売会のオーナーやお店の印を書きかえられない・営業中に会計を消せない
- 合言葉は、期限切れ・まちがい・違う役割・**2回目**では使えない。端末の時計で時刻を書けない。1時間より長い合言葉は作れない。入らずに合言葉だけを消せない
- CD は、会計を読めない・書けない
- お客様は、自分の注文だけを作れて、自分の注文だけを読める。値段・状態を書きかえられない。受付を止めていると注文できない
- レストラン：開いている伝票を横取りできない・ほかのテーブルの伝票に注文を付けられない
- お店の印：だれでも読めるが一覧は出ない・ほかの人は行き先を書きかえられない・だれも消せない
- お店のオーナー：オーナーが足せる・その端末は販売会のオーナーになれる・ほかのお店の印を付けた販売会を作っても、そのお店には何もできない・自分を外して空のお店にはできない
- お店の鍵：オーナーだけが作れて読める・まちがった鍵・古い「持っています」・作り直す前の鍵では、オーナーになれない
- 外された端末は、すぐに読めなくなる。外された開店した端末は、自分をオーナーに戻せない
- 閉店した後は、片づけ（消すこと）ができる

アプリ本体も、エミュレーターにつないで通しで確かめています（開発用の試験。リポジトリの外）：
- 合流のお願い・許可・断る・合言葉・外す・お客様の注文・いつもの端末（54項目）
- 開店した端末の電池切れ・控えのオーナー・1回だけの合言葉・確かめる番号・お店の鍵・締め出し・知らないオーナーからの知らせ・返事が来ない時の開店（28項目）
- 注文・合流のお願い・端末の名前に、画面で動いてしまう書き方を入れても、レジ・KD・CD・印刷で動かない（ファストフード・レストランで各14項目）

## 5. 公開の手順（この順番で）

1. **アプリを、この版に更新する**（GitHub Pages に反映されるのを待つ）。
   - 使っている全部の端末で、アプリを開き直して、新しい版にしてください（ホーム画面のアプリは、一度閉じて開き直す）。
   - この版は、前の決まりの置き場でもそのまま動きます（先に更新して大丈夫です）。
2. **開いている販売会を、全部閉店する**。
   - 新しい決まりにすると、前の版で開いた販売会（オーナーの記録が無い）は、だれも読めなくなるためです。
3. **置き場の決まりを公開する**（どちらか）。
   - Firebase コンソール →「Firestore Database」→「ルール」に、リポジトリの `firestore.rules` の中身をそのまま貼って「公開」
   - または、パソコンで：`npm i -g firebase-tools` → `firebase login` → リポジトリのフォルダで `firebase deploy --only firestore:rules --project zemipos`
   - **前の版（合流のお願いを足した最初の版）の決まりを、もう公開していた時**は、アプリをこの版に更新したら、**すぐに**この版の `firestore.rules` を公開し直してください。前の版の決まりのままだと、合流の合言葉（1回だけの形）・お店の鍵・控えのオーナー・いつもの端末への知らせが使えません（合流のお願い・会計はそのまま使えます）。
4. **確かめる**：1台で開店 → もう1台で共有コードを入れて「合流のお願い」→ 番号が同じか見比べて、1台目で「許可」→ 会計が両方に出る。
5. **モバイルオーダーのQRコードを印刷し直す**（前のQRコード `order.html` だけのものは、お店を探さなくなったため使えません。新しいQRには `?s=…` が付きます）。テーブルのQRコードも同じです。
6. **控えを作る**（おすすめ）：信頼できる人のレジを1台「オーナーにする」。「お店の鍵」を作って印刷し、しまっておく。

## 6. Firebase・Google Cloud の設定（運営する人が行う）

| 項目 | すること | なぜ |
|---|---|---|
| ログインの方法 | Authentication → Sign-in method で「匿名」だけをオン（ほかはオフ） | 使わない入口を閉じる |
| 匿名アカウントの自動削除 | Identity Platform にした場合、「匿名ユーザーの自動クリーンアップ」は**オンにしない** | オンにすると、しばらく使わない端末のログインの印が消え、お店のオーナーでなくなる |
| 承認済みドメイン | Authentication → Settings → 承認済みドメインを、アプリのドメイン（例：`inocozuchi.github.io`）と `localhost` だけにする | ほかのサイトから、このプロジェクトでログインさせない |
| APIキーの制限 | Google Cloud コンソール → 認証情報 → APIキー →「アプリケーションの制限：ウェブサイト」にアプリのドメインを入れ、「APIの制限」で Firestore・Identity Toolkit・Token Service だけにする | キーは公開されているので、使える場所と使い道をしぼる |
| App Check（強くおすすめ） | Firebase コンソール → App Check で reCAPTCHA（v3 か Enterprise）を登録し、Firestore を「適用」にする。アプリ側に読み込みを足す作業が要ります（必要になったら一緒に作業します） | 決まりは守れても、機械で大量に匿名ログインして、注文やお願いを大量に送ることは止められない。App Check で、このアプリ以外からの通信を断る |
| 料金 | 無料プラン（Spark）のまま使うと、上限を超えた日はその日だけ止まる（請求は来ない）。従量課金（Blaze）にする時は、必ず「予算アラート」を設定する | だれかが大量に使った時に、思わぬ請求が来ないように |
| 使用量の見張り | Firestore の「使用状況」を時々見る | おかしな増え方に早く気づく |
| ほかの施設（`sites/`） | 同じプロジェクトを使う時も、置き場の名前は `events` のまま。**「ログインしていればだれでも読み書きできる」決まりを足さない** | 決まりは `events` だけを守っている |
| バックアップ | 売上の記録は各端末にも残る（閉店すると「過去の販売会」に保存）。置き場は閉店すると片づけるので、置き場のバックアップは要りません | — |

## 7. まだ残る心配と、その時の対処

| 心配 | 対処 |
|---|---|
| メンバーにした端末が、悪いことをする（会計を書きかえる等） | メンバーは信頼できる人の端末だけにする。知らない端末は「外す」。会計の記録の変更は操作の記録に残る |
| オーナーにした端末が、悪いことをする（ほかのオーナーを外す等） | オーナーは、ほかのオーナーを外せる（なくした端末を締め出すため）。オーナーにするのは、本当に信頼できる人の端末だけにする。乗っ取られた時は「お店の鍵」を使って取り戻し、「締め出す」 |
| お店の鍵の紙を、人に見られた・なくした | すぐに「お店の鍵を作り直す」。見た人がもうオーナーになっていたら「締め出す」 |
| 端末の画面のロックが無く、置き忘れた端末を触られる | 端末のロック（パスコード）を使う。KD・CD は会計の記録に触れないようにしているが、KD はレジと同じ権限なので、お客様の手の届く所に置かない |
| 知らない人からの合流のお願いが続く | 「合流のお願いを受け付けない」をオン。「全部断る」で消せる。同じ名前でも、確かめる番号を見比べる |
| お客様の、いたずらの注文 | 店頭で受け取らなければ、売上には入らない（未払いのまま）。続く時は、モバイルオーダーの受付を止める。値段はレジで数え直すので、安く会計されることはない |
| テーブルのQRコードを、ほかの席の人が使う | テーブルのQRの仕組み上、防げない（多くの店と同じ）。伝票の注文は、レジで取り消せる |
| レストランの伝票（テーブルごとの合計・支払い）が、共有コードを知っている人に読める | お客様の注文ページが、同じテーブルの伝票に注文を足すために読む必要がある。名前などは入っていない |
| クーポンのコードを当てずっぽうで探される | コードは長め（8文字以上）・数を限る（「上限」）にする。コードそのものは置き場に置かず、印だけを置いている |
| 大量の匿名ログイン・大量の書き込み（使用量を使い切られる） | App Check を入れる。無料プランなら、その日だけ止まる |
| 全部の端末の電池が切れたまま閉店しなかった販売会 | 置き場に残るが、メンバーしか読めない。次にその端末を開いた時に片づける。気になる時は、Firebase コンソールで `events` の古い物を消す |
| 置き場の決まりを書きかえる時のまちがい | 書きかえたら、必ず `tests/rules` の試験を通してから公開する |

## 8. お店に知らせること（公開する時に用意するもの）

- **利用規約** と **プライバシーポリシー**：`docs/利用規約_案.md`・`docs/プライバシーポリシー_案.md` に案を置きました。公開する前に、運営する団体で中身を決め、できれば専門家に見てもらってください。決まったら、アプリから見られる場所（ホームページなど）に置き、アプリの中にもその場所を知らせると安心です。
- **問い合わせの窓口**（メールアドレスなど）：不具合・データを消してほしい時の連絡先。
- 端末のロック（パスコード）を使うこと、iPhone はホーム画面に追加して使うこと、控えのオーナーとお店の鍵を用意しておくことを知らせる。
