# 別の施設での利用と、キッチン表示（KDS）の検討

2026年9月時点の検討メモです。いまのアプリ（パン・クッキーの販売会用）を、ほかの施設でも使う場合と、
ファストフード店のような「注文 → キッチン → 呼び出し」の形に広げる場合について、
やり方・つまずく所・その解き方をまとめます。

大事にすること（これまでと同じ）

- **会計の速さを何より優先する。** 新しい機能のせいで、いまのレジが遅くなったり、画面が増えたりしないようにする。
- **いまのパン・クッキーの販売会の人には、新しい機能が見えないようにする。** 使わない機能のボタンや設定は出さない。
- FesRegi のように「何でも1つの画面に並ぶ」形にはしない。入口を少なく、1つの画面では1つのことだけをする。

| ③ App Clip | このアプリ（ウェブ）とは別に、iPhone 用のアプリ（Swift）を作る必要がある | 未着手。費用と手間が大きい（5章） |

### GitHub のアカウントは増やさなくてよい

1つの Claude のスレッドにつなげる GitHub アカウントは1つですが、**URLを分けるのにアカウントを増やす必要はありません**。
いまのリポジトリの中に施設ごとのフォルダ（`sites/施設名/`）を置くと、今のアプリのURLのうしろに
`sites/施設名/` を付けたURLが、その施設のアプリになります。

- 同じドメインに置くと、ふつうは端末の中の保存場所が1つになって記録が混ざりますが、
  施設ごとの印（`data/site.js` の `id`）を保存の名前の頭に付けるようにしたので、混ざりません。
- 共有（Firebase）も、施設ごとに別のプロジェクト（または別の置き場の名前）にするので混ざりません。
- 施設ごとにドメインまで分けたくなった時は、GitHub の**組織（Organization）**を作る方法があります。
  組織は同じアカウントのまま無料で作れ、`組織名.github.io` という別のドメインになります
  （Claude からその組織のリポジトリを使うには、GitHub の設定でアクセスを許可します）。
  いまの段階では、フォルダを分けるだけで十分です。

## 2. 別の施設で使う時（②）

### 2-1. 同じURLでモードを切り替える形の問題

同じURLで「施設A／施設B」を選ぶ形にすると、次のことが起きます。

1. **端末の中のデータが混ざる。** ブラウザは、同じURL（正確には同じドメイン）のアプリに1つの保存場所しか渡しません。
   同じiPadを両方の施設で使うと、過去の販売会・商品・設定が同じ場所に入ります。
2. **「開いている販売会」の一覧に、ほかの施設の販売会が出る。** 共有の置き場（Firebase）が1つなので、
   施設Bの人が施設Aの販売会に合流できてしまいます。4けたの共有コードも、施設をまたいでぶつかります。
3. **選び間違いがそのまま売上の混ざりになる。** 当日の朝に施設を選び間違えると、その日の売上がもう一方の施設の記録に入ります。
   取り返しがつきにくい種類の間違いです。
4. **防ぐには「ログイン」が必要になる。** 施設ごとに見られるデータを分けるには、Firebase の認証と、施設ごとの読み書きの決まり（セキュリティルール）が要ります。
   いまの「コードだけで合流できる」手軽さが失われます。
5. **画面が増える。** 施設の選択・切り替え・確認の画面が、毎回の開店に加わります。

### 2-2. 施設ごとに別のURLにする形（おすすめ）

プログラム（`index.html`）は1つのまま、**施設ごとに違うのは `data/` の設定ファイルだけ**にして、
それぞれ別のURLに置きます。

- 端末の保存場所がURLごとに分かれるので、**データが混ざることは仕組みの上で起きない**
- Firebase も施設ごとに別のプロジェクトにすると、共有の置き場・使える量・費用も分かれる
  （施設Bの販売会が、施設Aの「開いている販売会」に出ることは無い）
- 施設ごとに商品・領収書の店名・客層の分け方（学生／教員／職員 など）を変えられる
- 不具合を直すと、同じプログラムなので**全部の施設に同じ修正が届く**
- 当日の操作は、いまとまったく同じ（施設を選ぶ画面が無い）

### 2-3. 気をつけること（落とし穴）

- **GitHub Pages で `https://inocozuchi.github.io/pan-pos/` と `https://inocozuchi.github.io/別の名前/` のように置くと、
  ドメインが同じなので端末の保存場所が同じになり、データが混ざります。**
  施設ごとにドメインを分ける（Firebase Hosting の `施設名.web.app`、Cloudflare Pages、独自ドメインのサブドメインなど）か、
  アプリ側で保存の名前に施設の印を付ける必要があります。
- 施設ごとにブランチを分けてコピーすると、修正を毎回両方に入れる手間が出て、片方だけ古くなりがちです。
  **1つのリポジトリの中に施設ごとの `data/` を置き、公開の時に組み合わせる**形が保守しやすいです。

## 3. キッチン表示（KDS）とモバイルオーダー（③）

### 3-1. できるか

できます。いまのアプリには、KDS に要る土台の多くがすでにあります。

| KDS に要るもの | いまあるもの |
|---|---|
| 端末どうしで注文をすぐ届ける | 共有（Firebase のリアルタイム同期・会計の二重登録の防止・通信が切れた時の後送り） |
| キッチン用・呼び出し用の画面 | 「お客様用の表示」という役割の仕組み（同じ販売会に、レジ以外の役割で入る） |
| 端末ごとにできることを分ける | この端末を制限（ロック） |
| その場で端末を足す | QRコードで合流 |
| 品切れ・在庫をそろえる | 共有中の残数（カート・予約・送信中の分も数える） |
| 商品の色分け | 分類ごとの色 |
| 売上の集計 | 集計・PDF・CSV（ここにチャネル別・状態別を足す） |

### 3-2. 店舗モードの形

FesRegi の「店舗モード」の考え方（やることに合わせて、キッチン・モバイルオーダー・テーブルの使い方がまとめて切り替わる）は良い案です。
ただし、このアプリでは次のようにします。

- **店舗モードは施設ごとの設定ファイル（`data/shop.js`）で決める。** 既定は「既製品の販売（パン・クッキーの販売会）」
- 既製品の販売のアプリでは、**店舗モードを選ぶ画面を出さない**（設定のメニューも1行も増やさない）
- 文化祭などで使うアプリ（別のURL）だけ、「キッチン調理＋呼び出し」などのモードにする

| モード | 内容 | 時期 |
|---|---|---|
| 既製品の販売（既定） | いまのアプリ。レジで会計したら完了 | いま |
| キッチン調理＋呼び出し | レジの注文がキッチンの画面に出る。作り終えたら番号で呼び出す | 第2段階 |
| ＋モバイルオーダー | お客様のスマホから注文。キッチンに届き、受け取りの時にレジで会計 | 第3段階 |
| カフェ・座席あり | 席ごとの注文と会計 | そのあと |

### 3-3. 注文の流れ

```
[レジ] 会計（先払い）─┐
                      ├→ 受付 → 調理中 → 呼び出し → 受け渡し完了
[スマホ] 注文（後払い）┘                      └→（後払いなら）レジで会計
                                  取り消しは どの段階からでも（理由を残す）
```

注文ごとに持つ情報

- 番号（客No.と同じ）・受けた時刻・どこから（レジ／モバイル）
- 食べ方（持ち帰り／店内）
- 状態（受付・調理中・呼び出し・受け渡し完了・取り消し）と、それぞれの時刻（何分かかったかの集計に使う）
- 支払い（済み／未決済）

### 3-4. キッチンの画面（FesRegi の写真から学ぶこと）

取り入れたい所

- 注文を**カード**で並べ、カードの上に「#12・調理中・4分・レジ」のように、番号・状態・経過時間・どこからを1行で出す
- 商品の行ごとに丸を押して「できた」の印を付けられる
- カードの下に**大きなボタンが1つだけ**（調理開始 → 呼び出し → 受け渡し完了）と、小さな「戻す」
- 上の絞り込み（全て／調理中／受け渡し／完了）
- 後払いの注文は「レジで決済」と分かるボタンにする

このアプリで足したい所

- 商品の行は**分類の色**（パン・クッキー・ドリンクの色と同じ考え方）で塗り分け、遠くからでも分かるようにする
- 経過時間が長い注文は、色で知らせる（例：10分を過ぎたら黄色、15分で赤）
- 持ち帰り／店内をカードの見出しに大きく出す
- 呼び出し中の番号を、お客様向けの画面（いまの「お客様用の表示」を広げる）に大きく出す

避けたい所

- FesRegi の設定画面のように、開催日・店舗モード・3種類のコード（ログインコード・モバイルオーダーコード・共有コード）が1つの長い画面に並ぶ形。
  **スタッフが覚えるコードは共有コード1つ、お客様にはQRコード1つ**にする
- 売上のグラフが0時〜24時の目盛りのまま、営業した時間だけに1本の棒が立つ形（いまのアプリは営業した時間だけを出している）

### 3-5. つまずく所と、その解き方

| つまずく所 | なぜ困るか | 解き方 |
|---|---|---|
| **お客様のスマホから書き込めるようにする** | いまはスタッフの端末だけが書き込む前提。誰でも注文を書き込めると、いたずらの注文・他人の注文の書き換え・売上の改ざんができてしまう | Firebase の匿名ログインと、セキュリティルールで「お客様は自分の注文を1件ずつ作れるだけ・読めるのは自分の注文だけ」にする。金額はお客様の端末で決めず、レジで会計する時に計算し直す。App Check と、1台あたりの注文数の上限も付ける |
| **いたずらの注文で、キッチンが空回りする** | 後払いだと、来ない人の注文も作ってしまう | 「受付」のあと、混んでいる時は**レジで支払ってから調理**に回す設定を選べるようにする。受け取りに来ない注文は、一定時間で取り消し候補にする |
| **Firebase の無料の範囲を超える** | 注文の状態が変わるたびに、キッチン・レジ・お客様の端末が全部読み直す。例：注文1000件×状態の変化4回×見ている端末6台で約2万4千回の読み込み。お客様がメニューを開く分も足すと、1日5万回の無料の範囲を超えうる | 従量課金のプラン（Blaze）にし、使いすぎの上限と知らせを設定する。メニューは1つの文書にまとめ、お客様の画面は自分の注文だけを見る。金額は1日数十円〜数百円の見込み |
| **お客様への呼び出しの知らせ** | iPhone は、ホーム画面に追加していないページには通知を送れない | 注文した画面を開いたままなら、音と振動と画面で知らせる。あわせて、店頭の呼び出し画面に番号を大きく出す。通知は後から考える |
| **文化祭のWi-Fi・電波の混雑** | 注文が届かない・二重に届く | いまの「送信中の分を覚えて、つながったら送る」「同じ会計を二重に数えない」仕組みを注文にも使う。キッチンが止まっても、レジは会計を続けられるようにする（紙の控えに切り替える手順も用意） |
| **1つのファイルが大きくなりすぎる** | いまの `index.html` は1万3千行。キッチン・モバイルオーダーを同じファイルに入れると、直す時の影響範囲が広がり、パン・クッキーのレジの不具合の元にもなる | キッチンの部分は `index.html` の中の1つのかたまりにまとめ、**店舗モードがキッチンの時だけ動く**ようにした（泰山木では、画面にも処理にも出てこないことをテストで確かめている）。お客様の注文ページは、レジのプログラムを読み込まない別のファイル（`order.html`）にする |
| **本番中にアプリを更新してしまう** | 当日に更新が入ると、端末ごとに版が違って動きが合わなくなる | FesRegi の「開催日」の考え方を使い、開催日の前後は更新を止める（公開の仕組みで止める）。画面の隅に版の番号を出す |
| **試す場所が無い** | 本番の前に、キッチンまで通した練習ができない | 本番とは別の Firebase プロジェクト（練習用）を用意し、練習用のURLで通し稽古をする |

### 3-7. 作ったキッチンモード（設定 → 店舗モード →「ファストフード」）

（2回目の見直しで、次のように変えた：調理開始のボタンをやめて、注文が入ったらすぐ調理中。
行ごとの赤い「未」を押して消し、全部消えたら呼び出せる。持ち帰りは橙・店内は緑。
レジのカートを会計が終わる前から「会計中」として点滅させて出し、新しい注文は音で知らせる。
番号は、共有中はレジの端末ごとの文字＋数字（A1、B1…）、モバイルは M1…。以下は1回目の内容）


- レジの会計の窓に**「持ち帰り／店内」**（何もしなければ持ち帰り）。客層を決めていない施設では、客層の欄は出ない
- 会計すると、その会計が**注文**になり、下の**「キッチン」**のタブにカードで出る（予約のタブの場所。予約は設定から開ける）
  - カード：番号・状態・持ち帰り/店内・経過時間（10分で黄、15分で赤）・商品ごとの個数（分類の色の帯）
  - 大きなボタン1つで **調理開始 → 呼び出し → 受け渡し完了**。↶ で1つ前に戻せる。行を押すと「できた」の印
  - 絞り込み（全て・受付・調理中・呼び出し中・完了）と、**担当**（全部／フード／サイド／ドリンク。ドリンク係はドリンクの行だけ見る）
- お客様に向ける画面は2種類（4回目の見直しで分けた。下の 6c）。**お会計の表示**は金額とお釣り、会計が済むと呼び出しの番号。
  **呼び出し番号**は「お呼び出し中の番号」と「お作りしています」の番号だけを大きく出し、呼び出すと音が鳴る
- レジで会計を取り消す・直すと、キッチンのカードも取り消し・直しになる
- 注文の状態は、**売上の記録とは別の置き場**（`orders`）に置く。キッチンで何を押しても、売上は変わらない
- 閉店すると、注文もその回の記録に残る。閉店して片づける時は、注文の置き場も消す
- 売上集計に**「注文と提供時間」**（注文から呼び出しまでの平均・真ん中・最長、どの区間で待たせたか、時間帯ごと、待たせた注文、持ち帰りと店内の売上）
- 操作マニュアルに「キッチンで作る・番号で呼ぶ」（キッチンのお店だけに出る）

## 4. モバイルオーダー（お客様のスマホから注文）

**作ったもの**：`order.html`（メニュー・持ち帰り/店内・注文・番号・あと何組・できたら音と画面）、
設定の「モバイルオーダー」（受付中/停止中・お知らせ・QRコード）、レジの「モバイルの注文（未払い）」から会計、
キッチンに「モバイル・未払い」の印、まだ払っていない分を残数から引く。以下は作る前の検討。

ねらい：QRコードを読むと注文の画面が開き（インストール不要）、注文すると番号が出て、
**「あと何組で受け取れるか」**が見え、できたら知らせが来る。行列に並び続けなくてよい。

### 4-1. 作り方

| 部分 | やり方 |
|---|---|
| 注文のページ | `order.html` を別に作る（レジのプログラムは読み込まない。軽く、すぐ開く）。商品・値段・品切れは販売会の文書から読む |
| 注文する | お客様のスマホは Firebase の匿名ログインで、自分の注文を1件作るだけ。キッチンの画面に「モバイル」の印で出る |
| あと何組 | 注文の置き場の中身をお客様に見せない。スタッフ側が「作っている番号の並び」だけを1つの文書（`live/queue`）に書き、お客様のページはそれと自分の注文だけを読む。自分より前にある番号の数が「あと何組」 |
| 支払い | 受け取りの時にレジで会計（後払い）。レジの画面で番号を選ぶと、その注文の中身がカートに入る。混んでいる日は「レジで払ってから作る」も選べるようにする |
| 品切れ | 今の共有の残数を使い、残り0の商品は注文のページで選べなくする |

### 4-3. 先に決める・変えること

- Firestore のルール：いまは「匿名ログインしていれば全部読み書きできる」。お客様のスマホもログインするようになるので、
  **お客様は自分の注文を作るだけ・読むのは自分の注文と `live/queue` だけ**、売上や予約には触れない、というルールに変える
  （この変更は、泰山木のレジの動きには影響しない形で書ける）
- いたずら対策：1台あたりの注文数の上限、App Check、受け取りに来ない注文を一定時間で取り消し候補にする
- 費用：お客様がページを開くたびに読み込みが増えるので、無料の範囲（1日5万回）を超えうる。Blaze プランにして、使いすぎの上限と知らせを設定する

## 5. App Clip について

App Clip は、iPhone でアプリをインストールしなくても、アプリの一部をすぐ使える Apple の仕組みです。
ただし、**App Clip になれるのは App Store に出す iPhone のアプリだけ**で、ウェブのページ（このアプリ）はそのまま App Clip にはできません。

| 必要なもの | 内容 |
|---|---|
| Mac と Xcode | Swift で iPhone のアプリを作る |
| Apple Developer Program | 年会費がかかる（団体で入るなら団体の手続きも要る） |
| 本体のアプリ | App Clip は、本体のアプリにくっつけて出す決まり |
| App Store の審査 | 出すたびに数日かかる。本番の直前の直しが間に合わないことがある |
| ドメインの設定 | 注文のURLと App Clip を結びつける設定ファイルを、このアプリのドメインに置く |
| 通知のサーバー | できあがりの知らせを送るサーバー（Cloud Functions と Apple の通知の鍵） |

- よいところ：QRを読むとすぐ開き、**許可を聞かずに8時間まで通知できる**（できあがりの知らせにぴったり）
- 気をつけること：iPhone だけ（Android の人にはウェブのページが要る）。コードが2つ（ウェブと Swift）になり、直す手間が倍になる。
  ウェブのページをそのまま包んだだけのアプリは、審査で断られることがある
- おすすめ：まずウェブのモバイルオーダー（4章）で運用して、「通知が無くて困る」ことがはっきりしてから App Clip を考える。
  その時は、注文の置き場（Firestore）はそのまま使えるので、作るのは iPhone の画面の部分だけになる

## 6c. 端末の役割・待ち時間・受け取り時間（4回目の見直し）

### 端末の役割
それまでは「お客様用の表示」1つに「呼び出し番号だけを映す」のスイッチがあり、金額の画面と呼び出しの画面の区別が分かりにくかった。
**「設定 → この端末の役割」**に一覧で並べ、押せばその場で切り替わるようにした（合流の画面・QRコードでも同じ4つから選べる）。

| 役割 | 何をする端末か | 中身 |
|---|---|---|
| レジ | 商品を打って会計する | 今までどおり |
| キッチン | 注文のカードだけを出す（会計しない） | レジと同じく販売会のデータを持つ。営業中はレジのタブを出さず、レジの画面を開こうとしてもキッチンの画面にする。1台だけで営業中の端末はキッチンにできない（レジが無くなるため） |
| お会計の表示 | レジの横でお客様に金額を見せる | 待ち受けは「いらっしゃいませ」。会計が済むと「ありがとうございました」と**呼び出しの番号** |
| 呼び出し番号 | 受け取り口に置く | 会計中も番号だけ。呼び出しの注文だけを受け取る（お会計の表示は受け取らないし鳴らさない） |

既製品の販売では「レジ」「お客様用の表示」の2つだけ。キッチンと呼び出し番号は、販売会がファストフードの時だけ選べる（合流の画面は、コードを調べて販売会がファストフードと分かった時点で4つにする）。

### 払うタイミング（運用）
| 注文 | 払う時 |
|---|---|
| 店頭で持ち帰り | その場で会計（会計が済むと番号が付き、キッチンへ） |
| 店頭で店内飲食 | その場で会計、または「後で会計」で注文だけ出して帰る時に会計 |
| モバイルオーダー | 持ち帰りは受け取りの時、店内は帰る時に「未会計の注文」から会計 |

まだ払っていない**持ち帰り**の注文は、KDで「受け渡し完了」を押せない（カードに「未会計（会計してから渡す）」と出る。レジで会計すると押せるようになる）。
店内の注文は先に渡せる（「受け渡し完了（お代は帰る時）」。未会計の一覧には残る）。5回目の見直しで、店内で食べて帰る時に払う運用に戻した。

閉店する時に未会計の注文が残っていれば、件数と番号を見せて確かめる（来なかった注文もあるので、止めはしない）。

### モバイルの待ち時間と受け取り時間
- `events/{コード}.mobile` に `wait`（分・0は出さない）、`pick`（受け取り時間を選べるか）、`lead`（何分前にキッチンへ出すか・既定10）、`ahead`（何分先まで選べるか・既定120）を足した
- お客様のページ：いちばん上に「いまの待ち時間 約◯分」。確かめる画面で「できしだい」か10分ごとの時刻を選ぶ（いちばん早い時刻は、`lead` と待ち時間を見込んだ時刻）。注文に `pickupAt` を入れる
- キッチン：`pickupAt − lead` までは**「時間指定」**のタブに取っておき、「全て」「調理中」・ナビの数・呼び出し番号の「お作りしています」には入れない。時刻になると「全て」に出てきて音が鳴る。「いま作り始める」で早く出せる（`rel` に時刻を書く。書いた注文は、端末の時計が少しずれていても取っておかない）
- 経過時間と「注文と提供時間」の集計は、作り始めた時刻から数える（時間指定で待っていた時間を入れない）
- 「予約」という名前は、設定から開く予約の機能と取り違えるので使わない

| 戻る | いつも押す前にいた画面へ。閉店中にKD・CDを押すと、試し映しは出さず、その役割で合流する画面を開く（戻るで役割の画面）。CDをやめた時も、CDにする前の画面に戻す。未会計・予約から会計を開いて「戻る」を押すと、元の一覧に帰る（読み込んだカートは元に戻す） |
| 番号 | 頭の1文字＋4けた。レジの店内 E・レジの持ち帰り O・モバイルの持ち帰り M・モバイルの店内 T。千の位はどこで受けたか（モバイル 0、レジは開店・合流の時に 1、2…を決める。KD・CDは番号を取らない）。例 E1001・O2003・M0001・T0002-12（席12） |
| CD（待っている間） | 上から「いらっしゃいませ」→ 使える支払い方法 → 広告。支払い方法は、現金・コード決済・カード・電子マネー・金券を**形のピクトグラム**で表す（会社のロゴ＝商標は使わない）。広告は下の横長の枠（16:9）で、縦長の画像は高さに合わせて左右を空ける |
| CD（金額） | 合計はうすい面にまとめ（区切りの線は使わない）、けた数では大きさを変えない（5けたの幅で決める）。会計へ進んだ後は 合計点数・お預かり・不足・お釣り の4行をいつも出す（不足0円は薄く）。縦向きでは合計を下の端から少し上げる。左右の2段組は横向きの時だけ |
| 注文の書き込み | レジとKDが同じ注文を同時に書いても消し合わないよう、変えた項目だけを送る |
| 時間指定 | 受け取りの何分前にKDへ出すか（はじめ10分）を、KDの「時間指定」と設定で選ぶ。早く来た時は KDの「いま作り始める」か、未会計の「いますぐKDに出す」。出てきた注文は見出しを点滅（「未」を消すと止まる） |
| KDの担当 | 担当の商品を上に、担当でない商品は下に灰色で（押せない）。作りかけの合計は分類ごとに区切る |
| モバイル | 確かめる画面では前の番号を出さない。受け渡しが済むと、お礼を少し出して番号を消し、はじめの画面へ。番号にお店の名前を付ける。QRはお店（販売会）ごとに1つで、持ち帰り・店内・席は注文の時に選ぶ |
| 設定 | 「セット割・クーポン」と「売上目標」に分けた。印刷は「レシート」「領収書」。開店の準備では、割引と目標を半分の幅で横に並べて、背の低いスマホでもスクロールなしにした |
| そのほか | 会計記録で客属性を押した時に全部のカードが動き直していた（点滅して見えた）ので、描き直しの時は動きを付けない。明暗を切り替えた時に上の帯の色が変わらないことがあるので、帯の色の指定を作り直す |

## 7. ①（前回の集計PDFの取り込み）で残っていること

- Chrome で作ったPDFは、7月からいまの版までの29通りの形で読めることを確かめました。
  iPhone・iPad の Safari で保存したPDFは、この環境では試せていません。文字が入っているPDFなら同じように読めるはずですが、
  もし数字がずれた時は、保存の前の確かめる画面で直せます。
- 写真やスキャンのPDFは文字が無いため読めません（手で入れる）。読めるようにするには文字認識（OCR）が要り、
  数字の読み違いが起きやすいので、今回は入れていません。
