# 複数端末リアルタイム同期（Cloud Firestore）ガイド

このアプリは、**設定を入れたときだけ**複数端末で売上をリアルタイム共有できます。
設定が空、または通信できないときは、**従来どおり各端末の中だけで安全に動作**します（オフラインでも会計は止まりません）。

---

## 1. できること
- 同じ「**お店**」に入れた端末どうしで、**会計・取消・修正・客属性・在庫（残数）をリアルタイム共有**。
- 2台以上で**同時に会計**しても、売上を1つのリストに統合。集計・レポートも全端末分をまとめて計算。
- 在庫は「仕入れ数 − 全端末の販売数合計」で表示（売り越しに全端末で気づける）。

## 2. 有効化の手順（コンソール作業が済んだら）
Firebaseコンソール側（プロジェクト作成／Firestore作成／匿名認証ON／`firebaseConfig`取得／ルール公開）が完了している前提です。

1. `data/firebase-config.js` を開く。
2. 末尾の `window.FIREBASE_CONFIG = null;` を、コンソールでコピーした設定に置き換える：
   ```js
   window.FIREBASE_CONFIG = {
     apiKey: "…",
     authDomain: "…",
     projectId: "…",
     storageBucket: "…",
     messagingSenderId: "…",
     appId: "…"
   };
   ```
3. GitHubにコミット＆Push（GitHub Pagesに反映）。
4. アプリを開くと「開店・設定」に **🔗 複数端末で同時に会計する** の欄が出ます。

> Web用APIキーは公開前提の識別子なので、貼り付けても問題ありません。
> データ保護は下の「置き場の決まり」（販売会はメンバーの端末だけが読み書きできる）で行います。

## 3. セキュリティルール（置き場の決まり）
- 決まりは、リポジトリの **`firestore.rules`** です。Firebase コンソール →「Firestore Database」→「ルール」に中身をそのまま貼って「公開」するか、`firebase deploy --only firestore:rules` で公開します。
- 考え方・公開の順番・コンソールの設定は **`docs/一般公開の準備.md`** にまとめました。**公開の前に、開いている販売会を全部閉店してください**（前の版で開いた販売会は、新しい決まりでは読めなくなります）。
- 決まりを書きかえたら、必ず `tests/rules` の試験（エミュレーターで106項目）を通してから公開してください。

### 置き場の中身（お店のしくみ）
しくみは「端末はお店に入る。お店の端末だけが、そのお店の販売会を読み書きできる」だけです（図は `docs/一般公開の準備.md` とアプリの手引き）。
- `shops/{お店の印}` … お店。中身は印刷したQRコードの行き先 `{ event, name, open, at, by }` だけ。だれでも1件ずつ読めるが、一覧は出ない。消すことはできない（前の版の `owners` は残してあり、そこに書いてある端末はオーナーとして引きつげる）
- `shops/{お店の印}/members/{ログインの印}` … お店の端末 `{ role: owner|staff|display, name, kind, at, by, via, seen }`。ここにある端末だけが、お店の販売会を読み書きできる（CD＝display は会計を読めない）
- `shops/{お店の印}/adds/{合言葉}` … 「端末を入れる」の合言葉 `{ at, min, by }`。`at` は置き場の時刻。`min` 分（10分）だけ使える。オーナーだけが読める。`addcodes/{合言葉}` … 合言葉からお店の印を引く（知っている人だけが引ける）
- `shops/{お店の印}/requests/{ログインの印}` … お店に入れてほしいお願い `{ name, kind, role, t, at }`。合言葉が使える間だけ出せる。オーナーが「入れる」を押すとメンバーになり、お願いは消える
- `shops/{お店の印}/keys/{鍵}` … お店の鍵（オーナーだけが読める）。`shopkeys/{鍵}` … 鍵からお店の印を引く
- `shops/{お店の印}/claims/{ログインの印}` … 鍵を使う時の「この鍵を持っています」`{ k, at }`。10分のあいだ、自分をオーナーにできる
- `shops/{お店の印}/log/{id}` … お店の記録 `{ t, by, at, name, who }`（端末を入れた・外した・オーナーにした・鍵を使った・締め出した…）。書き足すだけで、直せない・消せない。オーナーだけが読める
- `events/{コード}` の `owner`（開店した端末のログインの印）・`shop`（お店の印。変えられない）。コードは6けたで、アプリの中だけで使う（人が打つことはない）
- `events/{コード}/cust/{ログインの印}` … お客様ひとりの注文の数 `{ n }`。注文と同時に1つ数え、1回の販売会で30件まで
- `events/{コード}/live/pub` … お客様に見せてよいお店の設定（名前・受付中か・モバイルオーダーの設定・消費税・セット割・コードで使うクーポンの印）。注文ページは販売会の文書ではなく、これを読む
- `events/{コード}/live/queue` … 待っている組 `{ s: [作り始める時刻…], at }`（品目・メモは入れない）
- 閉店すると、販売会の中身（会計・注文・注文の数・予約・端末の一覧…）を片づける

### モバイルオーダーを使う時（ファストフードのモード）
- お客様のスマホ（`order.html`）も匿名ログインして、同じ `events/{コード}` の下に書き込みます。
  - `orders/{注文}` … 注文（「モバイル・未払い」）
  - `live/mseq` … M1001、M1002 … の番号を数える文書
  - `live/menu` … メニューと品切れ（レジの端末が書き、お客様のページが読む）
  - `live/menuimg` … モバイルオーダー（標準の形）で出す商品の写真をまとめた文書（レジの端末が書き、お客様のページが読む）
  - `live/mhero` … モバイルオーダー（標準の形）のいちばん上の絵（レジの端末が書き、お客様のページが読む）
  - `live/alive` … お店の端末が動いている印 `{ at: 時刻, roundId }`。共有中の端末が5分ごとに書く。お客様の注文ページは、この印が1時間より古い時は注文を受けない
    （閉店をしないまま端末が止まった販売会に、注文が入り続けないように）。印が無い販売会（前の版で開いた所）は、開いてから24時間で同じ扱い。
- 印刷・掲示するQRコード（モバイルオーダー・レシート・POP・ポスター・テーブル）は、**お店の印**だけを入れた `order.html?s=お店の印`（テーブルは `&t=番号` も）。
  注文ページは `shops/{お店の印}` から、いま開いている販売会を開く。ほかのお店は出てこない（受付中のお店を全部探して並べる形はやめた）。
  販売会のコードは開店のたびに変わるので、コードを入れたQRを印刷すると次の開店から使えなくなるため。
- お客様の注文ページが読めるのは、`live/menu`・`live/menuimg`・`live/mhero`・`live/alive`・`live/pub`・`live/queue` と、**自分の注文だけ**（`orders` を `uid` でしぼって読む）。
### レストラン（テーブルと伝票）の時
- 置き場に次のものが増えます（閉店の片づけで、ほかといっしょに消します）。
  - `bills/{伝票}` … テーブルごとの伝票（伝票番号・テーブル・払った数・開いている／会計済み）
  - `tables/{テーブル}` … いまそのテーブルで開いている伝票の印
  - `live/bseq` … 伝票番号（0001、0002 …）を数える文書
- 伝票は **トランザクション**（まとめて読み書き）で開きます。ハンディ2台やお客様のスマホが同じテーブルに同じ瞬間に注文しても、伝票は1枚にまとまり、番号も重なりません。
- お客様（テーブルのQR）は、空いているテーブルの伝票を開くことと、そのテーブルの伝票に注文を足すことだけができます（開いている伝票の横取り・ほかのテーブルの伝票への注文は、`firestore.rules` が断ります）。
- 伝票の金額は、レジの商品の値段で数え直します（お客様のスマホが送った値段は使いません）。

### 商品の画像・消費税・委託商品・会計のメモ（今回ふえたもの）
- `img/{印}` … 商品の画像（レジのボタンの背景）。1品1文書で、`{ name: 商品名, d: 画像（JPEG・10KB前後）, at: 付けた時刻 }`。
  外した時は `d` を空にした文書を置き、ほかの端末からも消えます。閉店の片づけで `img` も消します。
  画像は商品の一覧（販売会の文書の `products`）には入れません（商品を直すたびに画像まで送らないように）。
- `imgh/{印}` … 商品の写真の**大きい控え**（POP・ポスターの印刷用）。`{ name: 商品名, d: 画像（JPEG・長い辺1000・200KB前後）, at: 付けた時刻 }`。
  `img` と同じ印・同じ時刻で置きます。ほかの端末は、POPで要る時にだけ1枚ずつ読みます（ふだんは読まない）。
  写真を外した時は文書ごと消します。閉店の片づけで `imgh` も消します。
- `live/hitsu` … 筆談（「レジの機能」の「筆談」をオンにした時だけ）。
  `{ open: 話している最中か, s: [お店が書いた物], c: [お客様が書いた物], clr: 消した時刻, req: お客様が始めた時刻, at, by }`。
  1つの書いた物は `{ i: 印, k: 't'（文字）|'d'（手書き）, at, t: 文字 | p: 手書きの線, r: 縦÷横 }`（それぞれ30件まで）。
  レジは `s`、CDは `c` だけを書きかえます（`set` の merge）。お店の「全部消す」「終わる」だけが両方を空にし、`clr` より前の物はどちらの画面にも出しません。
  オフの時は読みも書きもしません。`live` の中なので、閉店の片づけで消えます。`firestore.rules` では、CD（映すだけのメンバー）も筆談の文書にだけは書けます。
- 販売会の文書の `tax` / `taxBy` … 消費税の設定（使うか・分類ごとの税率・店内は10%・登録番号）。全端末でそろえます。
- 販売会の文書の `consign` / `consignBy` … 委託商品を使うか・手数料。委託先は商品ごとの `consign`（商品名の一覧の中）に入ります。
- `sales/{会計}` に増えた項目
  - `tax: { r: { 分類: 税率 }, eat: 店内か }` … その会計をした時の税率（消費税をオンにしている時だけ）。税額はここから計算します。
  - `items[].consign` … その品の委託先（委託商品の時だけ）。
  - `memo` … 会計記録のメモ（あとから書き足す。`update` で書きます）。
- 販売会の文書の `setRule` … セット割。`by: 'item'` の時は `needs` が商品名の並び（「商品で決める」）。
  置き場へは `by`・`needs`・`amount`・`kind` を毎回そろえて書きます（`merge` で書くと、前の `kind` などが残ってしまうため）。
- `firestore.rules` では、`img`・`imgh` を書けるのはレジ・KD などのメンバーだけです。

## 4. 当日の使い方

### 仕組みの前提（重要）
- 閉店中はレジの画面に「まだ開店していません」のカードが出ます（右上の「**開店・合流**」を押してもここに戻ります）。カードに「**新しく開店する**」と「**開いている販売会に合流する**」が並び、いま開いている販売会もその下に出ます。
- **開店は1台だけ**。開店すると必ず共有します（共有しない選択はありません。通信できない時だけ、その端末だけで開店します）。はじめて開店した端末が「お店」を作り、オーナーになります。
- **2台目からは「合流」**。お店に入れた端末には、カードに「合流する」が出るので、押すだけで入れます（名前・商品・それまでの会計は、開いている側のものを使います）。はじめての端末は、オーナーの端末の「端末を入れる」から1回だけ入れます。
- 合流できるのは**いま開いている販売会だけ**です。閉店済み・存在しない・12時間以上どの端末も使っていないコードには入れず、合流の操作で新しい販売会が作られることもありません。
- 「閉店する（集計して終了）」は**共有販売会そのものを終了する操作**です。全端末がいっしょに閉店し、それぞれに同じ集計が残ります。
- 一時的にこの端末だけ操作をやめたい場合は「この端末の利用を終える（ほかの端末は続ける）」。ほかにレジの端末が残っていない時は、先に「閉店して集計するか」を聞かれます。

### 閉店したコードの片づけ
- 閉店すると、**全端末が閉店を受け取って集計を残したあと**で、そのコードの中身（`sales` / `reservations` / `devices` / `live` と販売会の文書そのもの）を Firestore から削除します。
- まだ閉店を受け取っていないレジの端末（最後の知らせから30分以内）がいる間は削除しません。その端末が閉店を受け取った時に、あらためて削除します。
- 閉店から30分以上たっても残っている閉店済みの販売会は、どこかの端末で「合流する」の画面を開いた時に、ついでに片づけます。
- 電波が切れていて閉店を受け取れなかった端末は、つながった時に「片づけ済み」に気づき、**手元の会計で閉店して集計を残します**。
- これにより、同じコードがあとで使われても、前の回のデータが出てくることはありません。

### ケースA：ピーク時だけ2台体制にする
1. 端末1で「新しく開店する」。
2. 混雑してきたら、端末2の閉店中のカードに出ている販売会を押す。
3. 2台で同時に会計。売上・在庫はリアルタイムで両方に反映されます。
4. 落ち着いたら、端末2で「この端末の利用を終える」。販売会は端末1でそのまま続きます。
5. 最後に端末1で「閉店する」。

### ケースB：午前・午後で別の人のスマホに交代
1. 午前担当が端末1で「新しく開店する」。
2. 午後担当が端末2のカードに出ている販売会を押して合流（午前分の売上・残在庫がそのまま引き継がれます）。
3. 端末1は「この端末の利用を終える」。
4. 午後の営業終了時、端末2で「閉店する」。

### 1台で開店したあとで共有したくなった
- 「設定 → 複数端末で使う → ほかの端末と共有を始める」を押すと、ここまでの会計・在庫が共有の元になります。
- 別々に営業を始めてしまった端末どうし（同じお店）は、片方で「設定 → 複数端末で使う → お店の販売会に合流する」を開き、もう片方の販売会を押します（この端末の会計もいっしょに持っていきます）。

## 5. オフライン時の動作
- 通信が切れても会計は続行できます（端末内キャッシュに保存）。
- **回線が戻ると自動でまとめて同期**されます。
- 同期が一度も繋がらない端末は、その端末単独の売上として動きます（データは消えません）。

## 6. 客No.・在庫の注意
- 客No.は**全端末の会計を時刻順につなげた通し番号**です（重複しません）。会計履歴には、どの端末で記録したかが `［DA］` のようなラベルで併記されます。
- ごく僅かなタイミングのずれで、極めて短時間に複数端末でほぼ同時に会計した場合、通信状況によって客No.の順番が後から1つ入れ替わることがあります（金額・件数には影響しません）。
- 在庫はカート投入時点では減らず、**会計確定時**に全端末へ反映されます。同期中の在庫は「共有の仕入れ数 − 全端末の合計販売数」で計算されます。

## 6b. 予約（予約保留）は端末間で共有されません（重要な制限）
- 「予約保留」機能は、この機能の対象外です。**予約はその予約を受けた端末にしか保存されません**。別の端末からは見えず、清算もできません。
- 複数端末で運用中に予約を受けた場合は、**同じ端末で清算する**か、**他の端末の担当者に口頭・メモ等で伝えてから**清算してください。
- 予約管理タブには、複数端末同期が有効な間、この制限を知らせる注意書きが常に表示されます。
- シフト交代（端末1→端末2）の際は、端末1に未清算の予約が残っていないかを事前に確認してください（残っている場合、端末1の「閉店する」は予約が残っている旨のアラートでブロックされますが、これは端末1側の予約だけを見ての判定です）。

## 7. 同期をやめたい / 1台運用に戻す
- `data/firebase-config.js` を `window.FIREBASE_CONFIG = null;` に戻してPush。
- それだけで従来の1台運用（localStorage）に戻ります。データ構造は共通なのでバックアップ/引き継ぎ機能はそのまま使えます。

## 8. 実機での確認チェックリスト（重要）
本番のFirebase接続は開発環境ではテストできないため、公開後に以下をご確認ください。
- [ ] 2台で同じコードを開き、片方の会計が数秒でもう片方に出る。
- [ ] 客No.が2台の会計を通して重複しない（1,2,3…と続く）。
- [ ] 取消・品目修正・客属性入力が両端末に反映される。
- [ ] 在庫（残数）が両端末の販売を合算して減る。
- [ ] 1台を機内モードにして会計 → 復帰後にもう1台へ同期される。
- [ ] 端末2で後から同じコードを開店 →「参加しますか？」の確認が出て、参加すると端末1の売上・在庫を引き継ぐ。
- [ ] 端末2で「🚪 この端末の利用を終える」→ 端末1はそのまま継続できる。
- [ ] 端末1で「閉店する（集計して終了）」→ 集計・レポート・CSVが全端末分の合計になっている。
- [ ] 閉店済みのコードで再度「開店」しようとすると警告が出る。

## 9. 費用
- モバイルオーダーを使うと、お客様がページを開くたびに読み込みが増えます。文化祭のように人が多い日は、無料の範囲（1日5万回の読み込み）を超えることがあります。
  その時は従量課金（Blaze）にして、予算の上限と知らせを設定してください。
- 無料枠（Sparkプラン）で十分です（学内販売会の件数なら余裕。クレジットカード登録も不要）。
